Ajoute à Discuss un indicateur de traitement pour les conversations
privées avec les agents Hermes, convertit le Markdown de leurs réponses
en HTML assaini et actualise leur présence dans Odoo.

Comportement
------------

- La façade ``hermes.activity.publier`` reçoit les états ``working``,
  ``tool``, ``done``, ``error`` ou ``cancelled``. Elle valide que la
  conversation, le message et l'identité correspondent à une requête
  d'agent authentifiée.
- L'état est stocké sur le canal, puis rendu dans l'interface Discuss
  par les ressources JavaScript/XML du module. Les mises à jour plus
  anciennes, répétées ou reçues après un état terminal sont ignorées;
  l'historique affiché est borné.
- ``hermes.activity.repondre`` et les messages publiés par un compte
  Hermes passent le Markdown en HTML, puis l'assainissent. La prise en
  charge inclut notamment le gras, l'italique, le code, les liens
  HTTP(S), titres, listes et tableaux. Le HTML fourni par le modèle
  n'est pas interprété comme contenu actif.
- Une réponse écrite en HTML simple par le modèle est d'abord ramenée en
  Markdown, puis convertie comme les autres. Avec ``body_is_html``, le
  HTML déjà préparé par la passerelle est seulement assaini.
- L'invite d'approbation du framework Hermes (« Reply ``/approve`` to
  execute… ») devient quatre boutons : Approuver, Pour la session,
  Toujours, Refuser. Les commandes à taper restent écrites dessous.
- Un clic poste la commande au nom de la personne qui clique, membre du
  canal, sans ``sudo``. Il passe par ``/hermes/approbation`` en
  JSON-RPC. Sans JavaScript, le lien ``/hermes/repondre`` affiche une
  page de confirmation dont le formulaire POST porte le jeton CSRF.
  Aucun GET n'écrit : une image insérée dans un message ne peut donc pas
  approuver une commande.
- Le polling de la passerelle actualise la présence du compte. Une tâche
  planifiée marque hors ligne les agents sans heartbeat récent.

Accès et dépendances
--------------------

Dépend de ``mail`` et ``hermes_n1_audit``. Les façades refusent les
appels qui ne proviennent pas d'un compte agent identifié et relié à une
conversation privée accessible. L'état technique ne peut pas être
modifié directement par RPC ordinaire.

Use Cases / Context
===================

Dans Discuss, une conversation privée avec un agent Hermes ne dit rien
de ce que l'agent fait : ni étape en cours, ni durée, ni outil appelé.
Ce module ajoute cet indicateur, met en forme les réponses Markdown de
l'agent et rend opérationnels les boutons d'approbation du framework. Il
est distinct de ``hermes_n1_audit``, qui possède la façade d'écriture
métier : ici, rien n'est écrit dans les objets métier, seulement l'état
d'affichage du canal et le fil de discussion.

L'état vit dans un champ Json (``hermes_activity_state``) du canal, mais
son écriture directe est refusée hors superutilisateur : seule la façade
``hermes.activity.publier`` l'alimente, après avoir vérifié que l'appel
vient d'un compte agent et que le message source est celui d'un
demandeur authentifié (règle empruntée à ``hermes_n1_audit``). Les mises
à jour sont ordonnées par ``message_id`` puis ``sequence`` : les plus
anciennes, les doublons et tout ce qui arrive après un état terminal
sont ignorés, et l'historique est borné aux 50 dernières étapes.

Le Markdown est converti en HTML selon un ordre non négociable : tout
est échappé d'abord, seules les balises voulues sont réintroduites
ensuite ; le HTML fourni par le modèle n'est jamais exécuté. Les boutons
d'approbation postent la commande au nom de la personne qui clique, sans
``sudo``, et aucun GET n'écrit. La présence des agents est rafraîchie
par le polling de la passerelle, et une tâche planifiée les marque hors
ligne après trois minutes sans heartbeat. Les groupes reconnus sont ceux
de ``hermes_n1_audit``, ``hermes_n2_support`` et ``hermes_n3_infra``
quand ces modules sont installés.

Installation
============

Aucune dépendance externe : le module ne déclare ni dépendance Python ni
binaire (``external_dependencies`` absent) et s'installe comme un module
Odoo standard. Il dépend de ``mail`` et ``hermes_n1_audit``, installés
automatiquement.

Si ``hermes_n2_support`` ou ``hermes_n3_infra`` sont installés, leurs
groupes d'agent sont reconnus en plus ; sans eux, seuls les agents N1 le
sont (les références sont résolues avec ``raise_if_not_found=False``).
La tâche planifiée d'expiration de présence est créée à l'installation :
rien à lancer à la main.

Configuration
=============

Aucun réglage propre, vérifié dans le module : il n'expose ni
``res.config.settings``, ni paramètre système, et ne déclare aucun
groupe — son manifeste ne charge que ``data/presence_cron.xml``. Rien à
configurer.

Les droits d'accès sont ceux des modules voisins : les façades
reconnaissent les groupes ``group_agent`` de ``hermes_n1_audit``,
``hermes_n2_support`` et ``hermes_n3_infra`` quand ces modules sont
installés, et ``hermes_n1_audit`` reste la dépendance obligatoire. La
tâche planifiée « Hermes : expiration de la présence » est créée à
l'installation et tourne toutes les minutes.

Usage
=====

Pour utiliser ce module, il faut :

1. Ouvrir *Discussion* et une conversation privée avec un agent Hermes :
   le module n'ajoute ni menu ni réglage, tout se passe dans le fil.
2. Suivre le bandeau d'activité au-dessus de la zone de saisie : nom de
   l'agent, état (``working``, ``tool``, ``done``, ``error`` ou
   ``cancelled``), durée, et le détail *Étapes du traitement* avec la
   durée de chacune.
3. Sur une invite d'approbation du framework Hermes, cliquer l'un des
   boutons **Approuver**, **Pour la session**, **Toujours (permanent)**
   ou **Refuser** : la commande est postée au nom de la personne qui
   clique. Sans JavaScript, le lien ouvre une page de confirmation dont
   le formulaire porte le jeton CSRF.
4. Lire les réponses des agents mises en forme (gras, italique, code,
   liens HTTP(S), titres, listes et tableaux) sans que le HTML fourni
   par le modèle soit exécuté.

L'état affiché est borné à l'historique récent ; les mises à jour
anciennes, répétées ou reçues après un état terminal sont ignorées. Une
tâche planifiée marque hors ligne les agents dont la présence n'a pas
été rafraîchie.

Known issues / Roadmap
======================

L'état affiché est borné : la façade ne garde que les 50 dernières
étapes (``steps[-50:]``), et un seul message d'activité à la fois — une
mise à jour d'un ``message_id`` plus ancien est refusée. L'historique
complet d'un traitement n'est donc pas conservé dans le canal.

La mise à jour est un polling : le composant interroge ``lire`` toutes
les 3 secondes et considère l'état périmé après 90 secondes sans
rafraîchissement. Il n'y a ni notification push ni bus ; un onglet fermé
ne reçoit rien.

Les boutons d'approbation ne couvrent que quatre commandes (``approve``,
``approve session``, ``approve always``, ``deny``, avec les préfixes
``/``, ``!``, ``.``). Une autre invite du framework reste du texte à
taper. La conversion Markdown est volontairement petite (gras, italique,
code, titres, listes, tableaux, liens http(s)) : pas d'images, pas de
listes imbriquées.

La présence repose sur un heartbeat et une tâche planifiée qui marque
hors ligne après trois minutes : un agent qui cesse de poller est
annoncé hors ligne même s'il tourne encore.
