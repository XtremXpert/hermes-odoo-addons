Côté plateforme, le module crée et suit les tenants Proxmox : un tenant
est un pool du cluster, sur un serveur donné.

Depuis la fiche du tenant, *Créer le pool* poste le pool et son
commentaire sur l'API du serveur, *Relire les membres* rafraîchit le
nombre de machines du pool, et *Supprimer le pool* le retire du serveur
— à condition qu'il soit vide, car le module ne supprime jamais ses
membres. *Fiche serveur du tenant* crée la fiche ``proxmox.server``
correspondante, bornée à ce pool, que l'instance du tenant utilisera.

Toutes les opérations sont notées dans le fil de la fiche du tenant. Le
module ajoute son entrée sous le menu *Proxmox* fourni par
``proxmox_tenant``, et son accès est réservé au groupe **Proxmox —
Opérateur de plateforme**.

Use Cases / Context
===================

Un hébergeur qui vend des machines Proxmox doit créer, un par un, les
tenants de ses clients : un tenant est un pool du cluster, sur un
serveur donné, avec un identifiant de pool. ``proxmox_server`` porte ce
côté plateforme — créer le pool sur l'API, le relire, le supprimer sous
garde, et fabriquer la fiche serveur bornée à ce pool que l'instance
Odoo du tenant déclarera.

L'approche est volontairement prudente. La suppression est refusée tant
que le pool porte des membres : le module ne supprime jamais les
machines d'un client. Chaque geste est journalisé dans le fil de la
fiche du tenant, avec l'auteur et l'heure. La fiche ``proxmox.server``
du tenant est créée par recopie de l'URL et du jeton du serveur de
plateforme, avec ``allowed_pools`` limité au pool : c'est cette fiche,
et pas un réglage global, que l'instance du tenant utilisera.

Le module dépend de ``proxmox_tenant`` (modèles serveur, nœuds,
machines, pools, stockages et client API) et en réutilise les groupes :
son groupe *Proxmox — Opérateur de plateforme* implique *Proxmox —
Gestionnaire*, donc un opérateur de plateforme gère aussi le miroir. Son
menu s'ajoute sous *Proxmox*, fourni par ``proxmox_tenant``. Il n'ajoute
ni réglage, ni tâche planifiée.

Installation
============

Aucune dépendance externe : le manifeste ne déclare ni
``external_dependencies`` Python ni binaire, et le client Proxmox est
celui, en ``urllib``, de ``proxmox_tenant``. Le module dépend de
``proxmox_tenant`` et ``mail`` et s'installe comme un module Odoo
standard, après ``proxmox_tenant`` (Odoo respecte l'ordre des
dépendances). Il s'installe sur l'Odoo de la plateforme, pas sur celui
d'un tenant.

Configuration
=============

Un seul groupe est ajouté : **Proxmox — Opérateur de plateforme**,
visible dans l'onglet *Droits d'accès* de la fiche usager. Il implique
le groupe **Proxmox — Gestionnaire** de ``proxmox_tenant`` : un
opérateur de plateforme gère donc aussi les fiches serveurs, nœuds,
machines, pools et stockages.

La connexion au cluster n'est pas réglée ici : elle vient de la fiche
serveur choisie sur le tenant (*Proxmox* > *Serveurs*), donc de l'URL et
du jeton API portés par ``proxmox.server``. Le module n'ajoute ni écran
de réglages, ni paramètre système.

Usage
=====

Pour utiliser ce module, il faut :

1. Attribuer le groupe **Proxmox — Opérateur de plateforme** aux usagers
   de la plateforme, dans l'onglet *Droits d'accès* de la fiche usager.
2. Disposer d'au moins une fiche serveur dans *Proxmox* > *Serveurs*
   (``proxmox_tenant``) : elle porte l'URL et le jeton API utilisés par
   les appels.
3. Ouvrir *Proxmox* > *Tenants* et créer un tenant : nom, serveur
   Proxmox et identifiant du pool.
4. Sur la fiche, cliquer *Créer le pool* : le pool et son commentaire
   sont créés sur le serveur ; *Relire les membres* affiche ensuite le
   nombre de machines qu'il contient.
5. Cliquer *Fiche serveur du tenant* pour créer la fiche
   ``proxmox.server`` bornée à ce pool : c'est elle que l'instance du
   tenant déclarera pour ne voir que son périmètre.
6. *Supprimer le pool* retire le pool du serveur ; l'opération est
   refusée tant que le pool n'est pas vide.

Chaque geste est journalisé dans le fil de la fiche du tenant.

Known issues / Roadmap
======================

Limites connues
---------------

- **État distant en lecture seule** : ``remote_created`` et ``members``
  sont ``readonly`` ; l'état du pool se constate par *Créer le pool* /
  *Relire les membres*, jamais en éditant la fiche.
- **Suppression refusée sur un pool non vide** : le module ne supprime
  jamais les membres d'un pool ; il faut les retirer d'abord.
- **Aucune relecture automatique** : contrairement à ``proxmox_tenant``,
  le module n'a ni tâche planifiée ni rafraîchissement à l'ouverture ;
  le nombre de membres n'est à jour qu'après *Relire les membres*.
- **Jeton dupliqué** : ``action_creer_serveur`` recopie ``url`` et
  ``api_token`` du serveur de plateforme dans une fiche
  ``proxmox.server`` ; le secret existe alors dans deux fiches.
- **Un pool par serveur** : contrainte ``unique(server_id, pool_name)``.
- **Statut ``Beta``** : ``development_status`` vaut ``Beta``.
