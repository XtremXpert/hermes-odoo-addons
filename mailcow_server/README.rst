Couche **serveur** de Mailcow, réservée à l'exploitant de la plateforme
(xtremxpert.ca) : entretien de l'instance, suivi des versions,
préparation des accès remis aux exploitants de tenants.

Squelette pour l'instant — les outils d'entretien (état de l'instance,
relais SMTP, quarantaine globale…) viendront s'y ajouter. Les
exploitants de tenants (diverse-cite.com, …) n'ont pas à l'installer :
leurs outils vivent dans ``mailcow_tenant``.

Use Cases / Context
===================

L'exploitant de la plateforme (xtremxpert.ca) doit pouvoir entretenir
l'instance Mailcow elle-même — état du serveur, version, relais SMTP,
quarantaine globale — alors qu'un exploitant de tenant
(diverse-cite.com, …) n'administre que ses domaines, boîtes et alias.
Les deux métiers ne se recouvrent pas : un tenant n'a rien à faire dans
les outils d'entretien du serveur, et l'exploitant de la plateforme n'a
pas à porter les écrans d'exploitation d'un client. D'où deux couches :
``mailcow_tenant`` pour le tenant, ``mailcow_server`` pour la
plateforme.

Le module est pour l'instant une **coquille** : son seul code est un
``__init__.py`` vide, et son manifeste ne déclare ni modèle, ni vue, ni
donnée, ni règle d'accès. Il existe pour poser la frontière et la
dépendance : il dépend de ``mailcow_tenant`` et n'ajoutera ses outils
d'entretien que plus tard, sans que les instances de tenants aient à
l'installer. Son installation est donc sans effet visible.

Les modules voisins précisent la répartition : ``mailcow_tenant`` porte
l'exploitation d'un serveur (domaines, boîtes, alias, client API,
réglages de connexion), ``mailcow`` porte les écrans d'ensemble côté
usager, et ``mailcow_server`` restera l'outillage de l'exploitant de la
plateforme. Il ne s'installe que sur l'Odoo qui administre le serveur
Mailcow, jamais sur celui d'un tenant.

Installation
============

Aucune dépendance externe : le manifeste ne déclare ni
``external_dependencies`` Python ni binaire, et le module n'a aucun
fichier de données à charger. Il s'installe comme un module Odoo
standard, après ``mailcow_tenant`` qu'il déclare en dépendance (Odoo
installe celui-ci d'abord). Une seule instance le porte : l'Odoo de
l'exploitant de la plateforme, pas celui d'un tenant.

Configuration
=============

Aucun réglage propre : le module n'expose ni ``res.config.settings``, ni
paramètre système, ni groupe de sécurité — il n'a ni modèle, ni vue, ni
fichier de données et son ``__init__.py`` est vide. Il ne se configure
donc pas ; la connexion au serveur Mailcow reste celle posée par
``mailcow_tenant`` dans *Réglages* > *Mailcow* (URL et clé API), et les
droits restent les trois groupes Mailcow de ce module.

Usage
=====

Ce module n'a pas d'impact sur l'interface utilisateur.

C'est pour l'instant un squelette : il n'ajoute ni menu, ni vue, ni
réglage. Les outils d'entretien de l'instance (état du serveur, relais
SMTP, quarantaine globale…) viendront s'y ajouter ; l'exploitation d'un
tenant reste dans ``mailcow_tenant``.

Known issues / Roadmap
======================

Limites connues
---------------

- **Squelette sans fonctionnalité** : le module n'ajoute ni menu, ni
  vue, ni modèle ; son seul contenu est son manifeste et un
  ``__init__.py`` vide. Les outils d'entretien annoncés (état de
  l'instance, relais SMTP, quarantaine globale) ne sont pas écrits —
  ``readme/DESCRIPTION.md`` les donne comme à venir.
- **Aucun test** : le dossier ``tests/`` est absent, faute de code à
  éprouver.
- **Dépendance déclarée mais inutilisée** : le manifeste dépend de
  ``mailcow_tenant``, mais aucun code n'importe ses services. La
  dépendance est une intention de réutilisation (client API, groupes),
  pas un lien actif.
- **Statut ``Beta``** : ``development_status`` vaut ``Beta`` et la
  version est ``20.0.1.0.0``.

Pistes
------

- Écrire les outils d'entretien annoncés dans la description du module,
  en réutilisant ``mailcow_tenant/services/mailcow_client.py`` et ses
  groupes plutôt qu'un second client.
