Hermes — Runners

État des runners GitHub Actions auto-hébergés (ARC) qui exécutent la CI.

Le tableau de bord lit le cluster : chaque job attribué y crée un EphemeralRunner, avec sa phase, son identifiant GitHub et son ancienneté. Il montre aussi les pools (AutoscalingRunnerSet) et leur taux d’occupation, parce que la vraie question est « est-ce que la file avance ou est-ce que tout est pris ? ».

La distinction qui compte : le cluster sait quels runners existent, pas ce qui attend. Un job en file n’a pas encore de pod — il n’est visible que par l’API GitHub. Cette moitié n’est pas encore implémentée ; le module le dit plutôt que de laisser croire que « zéro runner » signifie « rien à faire ».

Use Cases / Context

La CI tourne sur des runners GitHub Actions auto-hébergés (ARC) dans Kubernetes. Quand un job reste en attente, rien ne le dit : il n’a pas encore de pod. Ce module répond à la seule question utile — est-ce que la file avance ou est-ce que tout est pris ? — en lisant les runners qui existent dans le cluster. Il est séparé de odoo_herd, qui gère les clusters, pour rester un simple tableau de bord.

Le serveur lit deux ressources personnalisées d’ARC (AutoscalingRunnerSet pour les pools, EphemeralRunner pour les pods) via le client Kubernetes que odoo_herd sait construire depuis ses kubeconfigs. L’ancienneté d’un runner est l’information clé : ARC ne garde un pod que le temps d’un job, donc un pod de plusieurs heures signale un job bloqué. L’occupation d’un pool est calculée sur maxRunners, pas sur le nombre de pods : 2/2 est saturé, 0/1 est libre, 0/0 signifie un pool en pause. L’agrégation est une fonction pure, testable sans cluster.

Une erreur sur un cluster est rapportée dans son entrée, jamais levée : un cluster muet ne masque pas les autres. Le module ne se connecte ni à GitHub ni directement au cluster côté navigateur : le serveur compose l’instantané, l’interface l’affiche avec l’heure de l’instantané et un rafraîchissement de 30 secondes. La moitié « file d’attente GitHub » n’est pas lue ici (voir Roadmap).

Installation

Aucune dépendance déclarée dans le manifeste, mais le module importe kubernetes au chargement (from kubernetes import client). Cette bibliothèque est déclarée par odoo_herd (external_dependencies.python), dont le module dépend : elle est donc installée avec lui. L’environnement Odoo doit fournir kubernetes, sinon le chargement du module échoue.

Dépend de odoo_herd et web, installés automatiquement ; aucun ordre manuel. Sans cluster actif déclaré dans Odoo Herd, le tableau s’ouvre mais ne montre aucun runner.

Configuration

Aucun réglage propre, vérifié dans le module : il n’expose ni res.config.settings, ni paramètre système, ni groupe, et son manifeste ne charge que views/menus.xml.

Le menu Runners est réservé au groupe standard base.group_system ; aucun groupe n’est déclaré par le module. La configuration réelle se fait dans odoo_herd : les clusters et leurs kubeconfigs sont lus dans k8s.cluster, et le module ne garde aucun jeton GitHub puisqu’il n’interroge pas GitHub.

Usage

Ouvrir Runners dans le menu principal.

Chaque ligne donne le pool, la phase, l’identifiant GitHub et l’ancienneté du pod.

Cette ancienneté demande une lecture prudente : un pool configuré avec minRunners > 0 garde un pod pré-provisionné en attente, qui peut afficher plusieurs jours d’âge sans qu’aucun job n’y soit bloqué. L’âge ne renseigne sur un job qu’une fois la phase connue — et le module ne lit pas encore le job lui-même. C’est pourquoi il est présenté comme une ancienneté, sans seuil d’alerte.

Le rafraîchissement est manuel (bouton) ou automatique toutes les 30 secondes. L’heure du dernier instantané est affichée : une donnée périmée présentée comme live est pire que pas de donnée.

Known issues / Roadmap

La moitié « file d’attente GitHub » n’est pas implémentée : runners_snapshot ne lit que le cluster. Un job en file n’a pas de pod, donc il n’apparaît nulle part ; le gabarit le dit à l’utilisateur (« Aucun runner actif. Un job en file n’a pas encore de pod… »). Lire la file demanderait un jeton GitHub et une requête à l’API, à ajouter ici.

L’occupation d’un pool est un rapport à maxRunners, pas une mesure de la file GitHub : un pool libre ne prouve pas que la file est vide. L’ancienneté d’un runner est calculée au moment de l’instantané ; elle n’est pas rafraîchie entre deux appels.

Les clusters actifs sont lus séquentiellement et sans délai d’attente paramétré : un cluster lent allonge l’appel pour les autres. Une erreur est rapportée dans l’entrée du cluster concerné, jamais levée, et il n’y a pas d’alerte globale. Le rafraîchissement de l’écran est de 30 secondes.
