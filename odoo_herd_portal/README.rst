Odoo Herd Portal
================

Portail client pour une production Odoo gérée par ``odoo_herd`` et ses
stagings (``/my/odoo``). Un client sans base peut en demander une (voir
« Nouvelle base »). Deux actions sur une base existante :

- **Resynchroniser le staging depuis la production** : copie neutralisée
  de la base et du filestore (``OdooStagingRefreshJob``, ``neutralize``
  forcé, source = la production du staging). Ouverte au client et aux
  agents, sans confirmation : le staging est jetable et ne peut jamais
  viser une production.
- **Passer la production au code du staging** : crée une demande de mise
  en production (``k8s.odoo.promotion``) qui fige l'image du staging par
  son empreinte (``…@sha256:``). Rien ne se passe tant qu'un **humain
  approbateur** ne l'a pas confirmée.

Flux
----

::

   agent / client ── demande ──► en attente ──► code par courriel ──► confirmée ──► planifiée?
                                                 (approbateur)                       │
   production ◄── mise à jour des modules ◄── image ◄── sauvegarde ◄──────────────────┘
                  (si demandée)            (spec.image seule)  (échec = production intacte)

Barrière humaine
----------------

- Seuls les **approbateurs** listés sur la production (onglet Portail)
  confirment, depuis le portail ou depuis le backend (bouton « Confirmer
  » de la mise en production, assistant ``k8s.odoo.promotion.confirm`` :
  mêmes contrôles privés, un mauvais code reste compté). La méthode est
  choisie par le serveur :

  - **double authentification activée** sur le compte (``/my/security``,
    ``auth_totp_portal``) → **code de l'application
    d'authentification**, vérifié par Odoo lui-même
    (``_check_credentials`` type ``totp`` : limite d'essais par
    utilisateur, code rejoué refusé). Le code par courriel est alors
    refusé ;
  - sinon, si la production a **« Exiger la double authentification »**
    → refus, avec un lien pour l'activer ;
  - sinon → **code à 6 chiffres envoyé par courriel** (10 min, 5 essais,
    une demande par minute), qui fonctionne aussi pour les comptes OIDC
    sans mot de passe Odoo. La méthode utilisée est enregistrée sur la
    mise en production (« Confirmée avec »). Seule une empreinte HMAC du
    code est stockée, illisible par l'ORM ; le courriel est un
    ``mail.mail`` supprimé après envoi, sans message dans le chatter
    (testé : un agent ne retrouve le code ni dans ``mail.message`` ni
    dans ``mail.mail``).

- **Hypothèse** : aucun agent ne peut lire la boîte courriel d'un
  approbateur. Vérifié en production le 2026-10-06 côté Odoo (les
  comptes ``hermes_n1``, ``hermes_n2``, ``hermes_n3``,
  ``hermes_n3_executor`` n'écrivent pas dans Mailcow et ne lisent pas
  ``mail.mail``), pas en dehors d'Odoo (accès au serveur de courriel,
  connecteurs de messagerie d'un agent). Si un agent peut lire ou
  détourner cette boîte, le code ne prouve plus rien : donner à
  l'approbateur une adresse hors de portée des agents. Cocher « Exiger
  la double authentification » sur une production supprime cette
  hypothèse : le secret TOTP reste sur le téléphone de l'approbateur.
- **Agents** = membres de « Opérateur de staging (agents) » ou d'un
  groupe d'un module ``hermes_*``. Ils ne confirment jamais, même
  ajoutés aux approbateurs, et ne peuvent modifier ni l'image d'une
  production, ni l'environnement, les approbateurs, le client,
  l'ouverture aux agents ou les comptes CI d'une instance — même en
  ``sudo`` (contrôle sur le groupe, jamais sur le contexte).
- La confirmation et le démarrage sont des méthodes privées
  (``_herd_*``), injoignables en RPC autrement que par les routes du
  portail et l'assistant du backend, qui passent l'utilisateur réel aux
  contrôles ; personne n'a de droit d'écriture sur
  ``k8s.odoo.promotion``.
- Une demande confirmée est figée (image, modules, horaire, instances).
  Une modification avant confirmation annule le code envoyé.
- Une seule mise en production à la fois par production ; au démarrage,
  une demande dont la production a changé depuis (image différente) est
  refusée au lieu de la ramener en arrière.
- « Terminée » sans modules signifie que l'image a été demandée à
  l'opérateur ; le déploiement lui-même se suit dans l'état de
  l'instance.
- Le changement d'image n'envoie que ``spec.image`` (pas
  ``_patch_to_cluster``, qui enverrait tous les champs non
  synchronisés). L'image précédente est gardée pour un retour arrière.

Nouvelle base (client sans base)
--------------------------------

Un client dont l'entité commerciale n'a encore aucune production voit la
tuile « Instances Odoo » à 0, avec « Ajouter une base ». Le wizard
``/my/odoo/new`` lui fait choisir une **offre** et un **nom** ; il crée
une demande ``k8s.odoo.instance.request`` (``BASE/0001``\ …). Rien n'est
créé dans le cluster avant qu'**un humain gestionnaire**
(``odoo_herd.group_k8s_manager``, jamais un agent) ne l'approuve dans
Odoo Herd → Demandes de bases.

::

   client ── demande ──► en attente ──► approuvée ──► production neuve, sans hôte public
                          (gestionnaire)              │ phase Running
                                                      ▼
         admin/admin remplacé par le compte du client (XML-RPC par le proxy de l'API)
                                                      ▼
          hôte réel posé, accès envoyé par courriel ──► staging clone_prod ──► prête

- **Offres** : modèles d'instance cochés « Proposé au portail » (onglet
  Portail du modèle), avec cluster, namespace et suffixe d'hôte. Hôtes :
  ``<nom>.<suffixe>`` et ``<nom>-staging.<suffixe>`` ; base ``<nom>``
  (tirets en soulignés) et ``<nom>_staging``.
- **Nom** : 3 à 30 caractères (minuscules, chiffres, tirets simples),
  noms réservés refusés, et libre partout : instances connues de l'herd,
  hôtes déjà servis, autres demandes. Une seule demande en cours par
  client ; aucune si le client a déjà une production.
- **Compte admin** : une base neuve (``odoo -i base``) a
  ``admin/admin``. La production est donc créée avec un hôte provisoire
  ``<nom>.herd-pending.invalid``, injoignable. Dès qu'elle est
  ``Running``, l'herd remplace ``admin/admin`` par le courriel du client
  et un mot de passe aléatoire, par XML-RPC à travers le proxy de
  Service de l'API Kubernetes, puis seulement pose l'hôte réel. En cas
  d'échec, la production reste injoignable et la demande passe en échec.
- **Mot de passe** : il n'existe que dans un ``mail.mail`` supprimé
  après envoi, jamais dans le chatter ; la transaction est validée dès
  ce courriel mis en file, avant de poser l'hôte et de créer le staging
  (étapes reprises par la tâche planifiée si elles échouent). Si l'envoi
  échoue, le courriel reste dans la file (Configuration → Technique →
  Courriels) jusqu'à son envoi ; s'il est perdu, réinitialiser le mot de
  passe du compte du client dans sa base (``odoo shell`` sur
  l'instance). Le mot de passe maître de l'opérateur est aléatoire et
  jamais montré (``list_db`` est coupé par l'opérateur). Le demandeur
  doit avoir un courriel : c'est son identifiant.
- **Staging** : créé ensuite par clonage neutralisé de la production
  (``clone_prod``), fermé aux agents. La production a pour client
  l'entité du demandeur, et le demandeur pour approbateur des mises en
  production.
- **Progression** : relancée à chaque changement de phase (webhook ou
  synchronisation), plus une tâche planifiée toutes les 5 min ; échec
  après 3 h sans nouvelles.

**Mise en place**, sur chaque cluster qui porte une offre : appliquer
``deploy/odoo-herd-clients.yaml`` (namespace ``odoo-clients``, et
``services/proxy`` pour odoo-herd dans ce seul namespace), copier le
secret de pull d'image dans ce namespace, et vérifier que le suffixe
d'hôte a un enregistrement DNS générique vers l'ingress.

**Copies neutralisées** : ``data/neutralize.sql`` désactive tous les
clusters, pour qu'un staging de l'herd ne crée, ne promeuve ni ne
resynchronise jamais rien sur un vrai cluster.

Flux de livraison de maison
---------------------------

1. **Staging** : resynchroniser ``maison-staging`` depuis la production,
   y déployer l'image de la branche ``20.0`` par son digest, puis
   installer ou mettre à jour les modules sur ``maison_staging`` et
   tester.
2. **Demande** : sur ``/my/odoo``, « Passer la production au code de ce
   staging », avec les *modules à mettre à jour* (``-u``) et les
   *nouveaux modules à installer* (``-i``), tels que testés sur le
   staging. Un agent peut préparer cette demande.
3. **Confirmation humaine** : un approbateur la confirme avec son
   application d'authentification. La promotion fait alors une
   sauvegarde, applique l'image (``spec.image`` seule), puis lance un
   seul ``OdooUpgradeJob`` (``-u`` et ``-i``).

``tools/promote-production.py`` ne sert plus qu'en secours.

Resynchroniser un staging
-------------------------

« Resynchroniser » remplace la base et le filestore du staging par une
copie neutralisée de sa production :

- **même cluster et même namespace :** l'opérateur clone la production
  (``OdooStagingRefreshJob``) ;
- **autre cluster** (diverse-odoo : prod sur rke01 OVH, staging sur le
  cluster maison) : il restaure la **dernière sauvegarde S3 terminée**
  de la production, filestore compris (``OdooRestoreJob``). Sans
  sauvegarde, la demande est refusée. Le cluster du staging doit avoir
  le secret S3 nommé dans ``k8s.s3.config``.

Pour les agents (RPC, groupe « Opérateur de staging »)
------------------------------------------------------

Sur un staging coché « Ouvert aux agents » :

.. code:: python

   env["k8s.odoo.promotion"].herd_deploy_staging(staging_id, "ghcr.io/…@sha256:…")
   env["k8s.odoo.promotion"].herd_resync_staging(staging_id)
   env["k8s.odoo.promotion"].herd_request_promotion(
       staging_id, modules="sale,stock", scheduled_at="2026-10-07 02:00:00"
   )

Comptes CI sur un staging fermé aux agents
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Un staging qui contient des données réelles (diverse-odoo) reste fermé
aux agents. Pour que la CI y demande quand même la promotion, inscrire
son compte dans « Comptes CI » du staging : il peut alors appeler
``herd_request_promotion`` et ``herd_staging_status``, **et rien
d'autre** (ni déploiement, ni resynchronisation, ni annulation). Le
compte CI reste un agent : il ne confirme jamais et ne touche jamais une
production.

Mise en place
-------------

1. Sur la production : client, approbateurs, et « Exiger la double
   authentification » pour une vraie production de client (onglet
   Portail).
2. Créer le staging (``environment = staging``,
   ``production_instance_id`` = la production), cocher « Ouvert aux
   agents » si besoin, ou seulement y inscrire le compte de la CI dans «
   Comptes CI ».
3. Donner le groupe « Opérateur de staging (agents) » au compte de
   l'agent, sans aucun groupe ``odoo_herd``.

Tâches planifiées toutes les 5 min : démarrer les mises en production
planifiées et abandonner celles sans nouvelles du cluster depuis 6 h ;
faire avancer les demandes de bases approuvées.

Tests : ``ADDONS=addons tools/test-modules.sh IMAGE odoo_herd_portal``.

Le client d'une instance
------------------------

Une instance sans client est invisible du portail : aucun utilisateur ne
la voit, et personne ne s'en aperçoit. Deux règles évitent que le lien
se perde :

- un staging hérite du client de sa production, à la création comme
  lorsqu'il y est rattaché après coup ; un client saisi explicitement
  n'est jamais écrasé ;
- une instance sans client porte le drapeau « Sans client », filtrable
  dans la recherche, pour que les instances importées de Kubernetes se
  voient avant d'être oubliées.

Use Cases / Context
===================

Un client d'une production Odoo gérée par l'herd n'a pas d'accès au
backend d'administration. Le portail lui donne une page ``/my/odoo`` :
l'état de sa production et de son staging, la resynchronisation du
staging depuis la production, et la demande de « passer la production au
code du staging ». Un client sans base peut aussi demander une nouvelle
base depuis le portail.

La règle centrale est que rien ne part en production sans un humain. Une
mise en production fige l'image du staging par son empreinte
(``…@sha256:``) et reste en attente jusqu'à la confirmation d'un
approbateur ; le code de confirmation est soit celui de l'application
d'authentification (vérifié par Odoo), soit un code à six chiffres
envoyé par courriel (10 minutes, 5 essais, une demande par minute), dont
seule une empreinte HMAC est stockée. Les agents sont reconnus à leurs
groupes, jamais au contexte : ils peuvent préparer une demande ou
déployer sur un staging ouvert, mais ne confirment jamais. Une demande
confirmée est figée, et une mise en production dont la production a
changé depuis est refusée au lieu de la ramener en arrière.

Le module ajoute aussi la demande de base : nom validé, hôte provisoire
``<nom>.herd-pending.invalid`` le temps de remplacer ``admin/admin`` par
le compte du client, puis hôte réel et envoi des accès par courriel. Les
copies neutralisées sont protégées par ``data/neutralize.sql`` (clusters
désactivés, comptes d'agents désactivés et clés API supprimées) : un
staging de l'herd ne pilote jamais un vrai cluster. Il dépend
d'``odoo_herd``, de ``portal`` et de ``auth_totp`` /
``auth_totp_portal``.

Installation
============

Aucune dépendance Python ou binaire propre : le manifeste ne déclare pas
d'``external_dependencies``. Le module dépend en revanche
d'``odoo_herd`` — dont les quatre dépendances Python (``kubernetes``,
``pyyaml``, ``boto3``, ``openupgradelib``) s'appliquent par transitivité
— ainsi que de ``portal``, ``auth_totp``, ``auth_totp_portal`` et
``mail``, installés avec lui.

Le fichier ``data/neutralize.sql`` n'est pas chargé à l'installation :
il est joué par ``odoo neutralize`` sur une copie (clusters désactivés,
comptes d'agents désactivés, clés API supprimées). La migration
``migrations/20.0.1.2.0/pre-migrate.py`` pose une valeur par défaut à
``ir.ui.view.visibility`` pour qu'une mise à jour du module ne casse pas
sur une base où ``website`` n'est pas encore chargé.

Configuration
=============

Le module n'a pas de réglages ``res.config.settings`` : il se configure
sur les fiches.

1. **Groupe agent** : attribuer **Staging operator (agents)**
   (``odoo_herd_portal.group_staging_operator``) aux comptes des agents.
   Ce groupe autorise le déploiement sur un staging, sa
   resynchronisation et la demande de mise en production ; il ne permet
   jamais de confirmer une promotion.
2. **Production** (*Odoo Herd* > *Odoo Instances*, onglet *Portal*) :
   *Client*, *Production approvers* et *Require two-factor
   authentication* (décoché par défaut). Sans client, l'instance est
   invisible du portail ; la recherche propose le filtre *Sans client*.
3. **Staging** (même onglet) : *Open to agents* (décoché par défaut) et
   *CI accounts*, qui peuvent seulement demander une promotion et lire
   l'état de livraison.
4. **Offres** (*Odoo Herd* > *Configuration* > *Instance Templates*,
   onglet *Portal*) : cocher *Offered in the portal* (décoché par
   défaut), puis renseigner le cluster, le namespace (qui doit déjà
   exister, avec le secret de pull et le Role de
   ``deploy/odoo-herd-clients.yaml``) et le suffixe d'hôte
   (enregistrement DNS générique vers l'ingress).
5. **Double authentification** : le module dépend de ``auth_totp`` et
   ``auth_totp_portal``. Un approbateur qui active la double
   authentification confirme avec le code de son application ; sinon, et
   si la production n'exige pas la 2FA, il reçoit un code par courriel
   (10 minutes, 5 essais, une demande par minute).
6. **Tâches planifiées** : deux tâches actives toutes les 5 minutes —
   démarrer les promotions planifiées et expirer celles qui sont
   bloquées, faire avancer les demandes de bases approuvées.

Usage
=====

Pour utiliser ce module, il faut :

1. Préparer les droits, le client, les approbateurs et l'offre publiée
   (voir Configuration) ; les agents ne confirment jamais une mise en
   production.
2. Côté client, ouvrir le portail à l'adresse ``/my/odoo``. Sans base,
   la tuile *Odoo instances* propose **Add a database** : choisir une
   offre et un nom, puis **Send the request**. Un gestionnaire (*K8s
   Manager*) approuve la demande dans *Odoo Herd* > *Database requests*
   avec **Approve and create**, ou la refuse.
3. Sur la page d'une base, **Resync staging from production** remplace
   la base et le filestore du staging par une copie neutralisée de la
   production.
4. **Move production to this staging's code** (ou **Update the
   production's modules** quand l'image est déjà la même) crée une mise
   en production : renseigner les modules à mettre à jour (``-u``), les
   nouveaux modules à installer (``-i``) et, éventuellement, l'heure.
   Rien n'est déployé tant qu'un approbateur ne confirme pas.
5. L'approbateur confirme depuis le portail, ou depuis la fiche de la
   mise en production (*Odoo Herd* > *Backup/Restore* > *Promotions*,
   bouton **Confirm**) : code de l'application d'authentification si la
   double authentification est active, sinon **Send me a confirmation
   code** puis le code reçu par courriel. Une sauvegarde de la
   production est prise avant tout changement.
6. Suivre les demandes et les promotions dans *Odoo Herd* > *Database
   requests* et *Odoo Herd* > *Backup/Restore* > *Promotions*.

Un agent appelle par RPC ``herd_deploy_staging``,
``herd_resync_staging`` et ``herd_request_promotion`` sur un staging
ouvert aux agents ; un compte CI peut seulement demander une promotion
et lire l'état de livraison avec ``herd_staging_status``.

Known issues / Roadmap
======================

Limites connues
---------------

- **Hypothèse du code par courriel** : le code à six chiffres ne prouve
  quelque chose que si aucun agent ne peut lire ou détourner la boîte de
  l'approbateur. Ce point est vérifié **dans Odoo** — les comptes
  ``hermes_n1``, ``hermes_n2``, ``hermes_n3`` et ``hermes_n3_executor``
  ne lisent ni ``mail.mail`` ni Mailcow — mais pas en dehors (accès au
  serveur de courriel, connecteurs de messagerie d'un agent).
  ``readme/DESCRIPTION.md`` recommande une adresse hors de portée des
  agents, ou la double authentification.
- **Double authentification non imposée par défaut** : *Require
  two-factor authentication* est décoché sur une production ; sans 2FA
  sur le compte de l'approbateur, le code par courriel est le seul
  facteur.
- **Déploiement non suivi en direct** : « Terminée » sans modules
  signifie que l'image a été demandée à l'opérateur ; le déploiement
  lui-même se suit dans l'état de l'instance
  (``readme/DESCRIPTION.md``).
- **Mot de passe d'une base neuve non récupérable** : il n'existe que
  dans un ``mail.mail`` supprimé après envoi. Si l'envoi échoue, le
  courriel reste en file ; s'il est perdu, il faut réinitialiser le mot
  de passe du compte par ``odoo shell`` sur l'instance — aucun
  self-service.
- **Resynchronisation inter-cluster conditionnée** : elle restaure la
  **dernière sauvegarde S3 terminée** de la production ; sans
  sauvegarde, la demande est refusée.
- **Staging fermé aux agents** : un compte CI n'y peut que demander une
  promotion et lire l'état de livraison — ni déploiement, ni
  resynchronisation, ni annulation.
- **Délais fixes** : confirmation valable 10 minutes, 5 essais, une
  demande par minute ; promotion sans nouvelles du cluster abandonnée
  après 6 h, demande de base en échec après 3 h ; deux tâches planifiées
  toutes les 5 minutes.
- **Dette de lint assumée** : ``.pre-commit-config.yaml`` exclut
  ``odoo_herd_portal`` et ``odoo_herd`` d'ESLint jusqu'à une PR dédiée.

Pistes
