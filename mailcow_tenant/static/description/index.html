Mailcow — tenant

Couche tenant de Mailcow : domaines, boîtes mail, alias et adresses de destination, administrés depuis Odoo par l’API v1 du serveur.

Les fiches se créent, se mettent à jour et se suppriment avec les boutons de l’écran, qui appellent l’API ; une synchronisation lit l’état du serveur et aligne la copie locale, sans jamais écrire sur Mailcow. Les listes se rafraîchissent d’elles-mêmes à l’ouverture si la copie date de plus d’une minute, et les fiches absentes du serveur sont marquées « non synchronisées » plutôt que supprimées.

Les mots de passe — initial d’une boîte, réinitialisation, mot de passe applicatif — sont fabriqués par Odoo, affichés une seule fois et stockés nulle part. Trois groupes règlent les droits : Lecture et synchronisation pour les agents, Utilisateur pour créer et mettre à jour, Gestionnaire pour supprimer, changer les mots de passe et administrer. Le module porte aussi les réglages de connexion et les données des tableaux de bord, dont les écrans d’ensemble vivent dans mailcow.

Use Cases / Context

Un exploitant de tenant (diverse-cite.com, …) doit administrer son serveur Mailcow depuis Odoo : domaines, boîtes mail, alias et adresses de destination, sans passer par l’interface d’administration de Mailcow et sans perdre la vue d’ensemble — quotas, occupation, comptes dormants, DKIM, TLS. Mailcow reste la référence ; Odoo en tient une copie interrogeable, qui alimente aussi les tableaux de bord du module mailcow.

L’approche est « copie locale, écritures explicites ». La synchronisation lit le serveur et aligne Odoo sans jamais écrire sur Mailcow : les listes se rafraîchissent seules à l’ouverture, au plus une fois par minute, et une fiche absente du serveur est marquée « non synchronisée » plutôt que supprimée — d’où la distinction entre une fiche jamais poussée et une fiche disparue. Les créations, mises à jour et suppressions passent par des boutons qui appellent l’API, avec les droits vérifiés dans le code (_exiger) et pas seulement sur le bouton : un bouton se contourne par RPC. Les mots de passe sont fabriqués par Odoo, affichés une seule fois et stockés nulle part ; une migration supprime même les colonnes que les versions précédentes gardaient.

Le module porte les réglages de connexion et trois groupes : Lecture et synchronisation (lire et aligner, le groupe des agents), Utilisateur (créer et mettre à jour) et Gestionnaire (cumule les deux, ajoute les suppressions et les mots de passe). La clé API peut venir de la variable d’environnement MAILCOW_API_KEY, ignorée sur une base neutralisée ; à défaut elle est rangée dans mailcow.api_key. Le périmètre d’un tenant se borne par le paramètre mailcow.allowed_domains. Les écrans d’ensemble côté usager vivent dans mailcow, l’entretien du serveur dans mailcow_server ; un pre_init_hook reprend les xmlids de l’ancien mailcow_admin pour que la mise à jour ne perde ni menus ni groupes.

Installation

Aucune dépendance externe : le client de l’API Mailcow est écrit avec urllib de la bibliothèque standard, et le manifeste ne déclare ni external_dependencies Python ni binaire. Le module dépend de base et mail et s’installe comme un module Odoo standard.

Deux particularités de mise à jour, sans effet sur une installation neuve : pre_init_hook adopt_mailcow_admin_xmlids reprend les xmlids de l’ancien module mailcow_admin, et migrations/20.0.2.1.0/pre-migrate.py supprime les colonnes de mots de passe que les versions précédentes gardaient. La variable d’environnement MAILCOW_API_KEY est facultative (voir Configuration).

Configuration

La connexion se règle dans Mailcow > Configuration, réservé aux administrateurs, et se retrouve aussi sous Réglages > Mailcow :

  • URL du serveur Mailcow : URL de base, sans /api/v1 ;
  • Clé API Mailcow : clé créée dans l’interface d’administration de Mailcow, section API ;
  • Tester la connexion : lit la version du serveur et le nombre de domaines qu’il renvoie ; un serveur qui ne renvoie aucun domaine est annoncé comme une alerte, pas comme un succès.

La variable d’environnement MAILCOW_API_KEY du conteneur Odoo l’emporte sur le réglage, qui est alors masqué ; elle est ignorée sur une base neutralisée, de sorte qu’un staging cloné n’agit jamais sur le vrai serveur. À défaut, la clé saisie est rangée dans le paramètre système mailcow.api_key.

Le périmètre du tenant se règle par le paramètre système mailcow.allowed_domains, une liste de domaines séparés par des virgules : une instance de tenant ne rapatrie que ces domaines ; vide, tout le serveur est visible.

Trois groupes sont déclarés dans la catégorie Mailcow de la fiche usager : Lecture et synchronisation (lire et aligner, sans écrire sur Mailcow ni voir de mot de passe — le groupe des agents), Utilisateur (créer, mettre à jour et ouvrir le menu) et Gestionnaire (cumule les deux, ajoute les suppressions et les mots de passe).

Usage

Pour utiliser ce module, il faut :

  1. Renseigner l’URL et la clé API dans Mailcow > Configuration (ou Réglages > Mailcow), puis cliquer Tester la connexion.
  2. Attribuer les groupes Mailcow dans l’onglet Droits d’accès de la fiche usager : Utilisateur (ou Gestionnaire) pour ouvrir le menu Mailcow ; Lecture et synchronisation pour un agent qui lit et synchronise par l’API sans passer par l’écran.
  3. Amener l’état du serveur dans Odoo avec Mailcow > Tout synchroniser, ou Synchroniser depuis Mailcow dans l’en-tête d’une liste ; Aperçu de la synchronisation décrit les changements sans rien écrire.
  4. Créer les fiches dans Mailcow > Objets > Domaines, Boîtes mail, Alias ou Adresses courriel, puis les pousser avec Créer sur Mailcow (ou Pousser la sélection vers Mailcow depuis la liste). Une fiche déjà synchronisée se met à jour avec Mettre à jour sur Mailcow.
  5. Sur une boîte, Changer le mot de passe et Mot de passe applicatif affichent le secret une seule fois ; En faire le fourre-tout crée ou réoriente l’alias @domaine.
  6. Les fiches retirées du serveur apparaissent sous Mailcow > Disparues du serveur, par objet ; on peut les archiver avec Oublier les fiches sélectionnées ou les supprimer localement, sans toucher au serveur.

Sur la fiche d’un usager, le bouton Créer la boîte Mailcow crée la fiche de boîte correspondant à son adresse courriel, à pousser ensuite vers Mailcow, si son domaine est déjà synchronisé (groupe Gestionnaire).

Les suppressions sur le serveur et les changements de mot de passe sont réservés au groupe Gestionnaire ; les réglages, aux administrateurs. Utilisateur crée et met à jour ; Lecture et synchronisation n’écrit jamais sur Mailcow.

Known issues / Roadmap

Limites connues

  • Clé API en clair quand l’environnement ne la fournit pas : hors MAILCOW_API_KEY, la clé est rangée dans le paramètre système mailcow.api_key, donc dans la base, ses sauvegardes et ses clones. La variable d’environnement est la voie recommandée.
  • Rafraîchissement borné à une minute : RAFRAICHISSEMENT_MIN_S = 60 ; une liste rouverte dans la minute garde la copie précédente, et il n’existe pas de webhook Mailcow pour forcer la relecture.
  • Disparition non destructive : une fiche absente du serveur passe à synced = False et reste en base ; le nettoyage est manuel (Oublier les fiches sélectionnées ou purge locale), jamais automatique.
  • Listage vide refusé : refuser_la_disparition_totale traite un serveur qui ne renvoie plus aucune entrée comme une panne probable. Après une suppression volontaire de tous les domaines côté Mailcow, la synchronisation refuse de conclure : il faut oublier ou purger les fiches localement.
  • Résultat incertain sur timeout : le client distingue une erreur franche d’un délai dépassé (RESULTAT_INCERTAIN) ; dans le second cas, la modification a pu être appliquée sur Mailcow et il faut synchroniser avant de réessayer.
  • Mots de passe non récupérables : ils ne sont jamais stockés (choix de conception) ; un mot de passe perdu se régénère, il ne se relit pas.
  • Mise à jour d’une base ancienne : le pre_init_hook adopt_mailcow_admin_xmlids et le script migrations/20.0.2.1.0/pre-migrate.py sont nécessaires pour reprendre les xmlids de mailcow_admin et effacer les colonnes de mots de passe ; une base encore sur l’ancien module en dépend.
