Neutralisation — garde-fou d’exécution

Une copie de staging ne doit rien déclencher : ni courriel, ni action planifiée.

odoo neutralize désactive les crons au moment du resync, mais cet état est écrasé dès qu’un module est installé ou mis à jour — le chargement XML recrée les ir.cron avec active = True, sans passer par toggle, le seul endroit où le cœur d’Odoo consulte database.is_neutralized.

Résultat : sur un staging, les crons se remettent à tourner après chaque déploiement, et le bouton « Exécuter manuellement » les lance même sans planificateur.

Ce module déplace le garde-fou à l’exécution : sur une base neutralisée, _callback refuse et journalise. Les trois voies sont couvertes — le planificateur, le déclenchement manuel et les appels programmatiques — parce qu’elles convergent toutes vers cette méthode.

Use Cases / Context

Une copie de staging ne doit rien déclencher : ni courriel, ni action planifiée. odoo neutralize désactive les crons au moment du resync, mais cet état est écrasé dès qu’un module est installé ou mis à jour : le chargement XML recrée les ir.cron avec active = True sans passer par toggle, le seul endroit où le cœur d’Odoo consulte database.is_neutralized. Le bouton Exécuter manuellement d’une tâche planifiée lance de même la méthode sans consulter le paramètre.

Le module déplace le garde-fou à l’exécution, en un seul point : la méthode _callback de ir.cron, par laquelle convergent le planificateur, le bouton manuel et les appels programmatiques. Sur une base neutralisée, elle refuse et journalise (_logger.info) ; sur une base normale, elle laisse passer. Il n’y a ni modèle propre, ni vue, ni donnée : c’est une surcharge de _callback, sans état à maintenir.

Le module s’installe sur toute base destinée à être clonée en staging ; il ne coûte rien ailleurs puisqu’il ne s’active que si le paramètre est posé. Il ne remplace pas la neutralisation d’Odoo, il la rend durable face au chargement des modules. Les envois de courriel directs et les appels d’API hors cron restent hors de son périmètre : ils ne passent pas par _callback.

Installation

Aucune dépendance externe : le manifeste ne déclare ni external_dependencies Python ni binaire, et le module n’a aucun fichier de données à charger. Il s’installe comme un module Odoo standard ; sa seule dépendance est base, qu’il surcharge (ir.cron._callback). Rien à faire après l’installation : le garde-fou s’active de lui-même sur une base neutralisée.

Configuration

Aucun réglage propre : le module n’expose ni res.config.settings, ni paramètre système, ni groupe de sécurité. Il ne lit qu’un paramètre du cœur d’Odoo, database.is_neutralized, posé par odoo neutralize, et n’ajoute ni menu, ni règle d’accès. Rien à configurer : sur une base neutralisée, le garde-fou refuse les crons ; sur une base normale, il est transparent.

Usage

Ce module n’a pas d’impact sur l’interface utilisateur.

Rien à faire après l’installation : sur une base neutralisée (paramètre database.is_neutralized posé par odoo neutralize), le planificateur, le bouton Exécuter manuellement des tâches planifiées et les appels programmatiques sont refusés et journalisés. Sur une base normale, le garde-fou est transparent.

Known issues / Roadmap

Limites connues

  • Périmètre limité aux tâches planifiées : le garde-fou ne couvre que ir.cron._callback. Un envoi de courriel ou un appel d’API déclenché hors d’un cron — par exemple depuis un bouton ou une action serveur — n’est pas filtré.
  • Aucune trace consultable depuis Odoo : le refus part au journal serveur (_logger.info), sans enregistrement en base. Sur une base neutralisée, il faut lire les logs pour constater qu’une tâche a été bloquée.
  • Aucun modèle, aucune vue, aucune donnée : le module ne se configure pas et n’affiche rien ; son seul indicateur est le paramètre database.is_neutralized, posé par le cœur d’Odoo.
  • Statut ``Beta`` : development_status vaut Beta.

Pistes

Aucune piste n’est consignée : le code ne porte aucun marqueur de travail en attente.
