Rassemble sur un seul écran l'état d'exploitation de l'infrastructure :
le parc Proxmox et les clusters Kubernetes.

Les chiffres Proxmox sont lus dans les miroirs locaux entretenus par
``proxmox_tenant`` — ouvrir le tableau ne contacte pas l'hyperviseur. La
date de la dernière synchronisation est affichée à côté des totaux, pour
qu'un chiffre périmé ne se lise pas comme une mesure en direct.

L'écran signale les nœuds hors ligne, la mémoire au-dessus de 90 %
(alerte) ou de 97 % (critique) et les machines arrêtées ; pour chaque
cluster connu d'Odoo Herd, il montre la joignabilité, les nœuds prêts et
les déploiements en deçà du nombre de réplicas voulu. Un cluster
injoignable est annoncé comme tel : il ne masque pas les autres.

Use Cases / Context
===================

L'exploitation a besoin d'un seul écran pour deux infrastructures qui se
répondent : le parc Proxmox et les clusters Kubernetes.
``proxmox_tenant`` synchronise déjà un miroir local, ``odoo_herd``
connaît déjà les clusters et leurs kubeconfigs ; ce module ne fait que
les lire et les présenter ensemble. C'est ce qui justifie de le séparer
des modules qui possèdent la donnée : il ne synchronise rien et n'écrit
rien.

Tout est calculé côté serveur au moment de l'ouverture, à partir des
miroirs : le tableau ne contacte jamais l'hyperviseur. Chaque chiffre
porte l'âge de l'instantané (``synced_at``), parce qu'une donnée périmée
présentée comme live est pire que pas de donnée. Les alertes sont des
ratios calculés à la lecture — mémoire au-dessus de 90 % en
avertissement, 97 % en critique — et non des seuils stockés. Pour
Kubernetes, chaque cluster est lu séparément : une exception est
capturée par cluster et rapportée dans son entrée, sans masquer les
autres.

Deux effets de bord utiles : l'agrégation Kubernetes est isolée dans
``summarize_kubernetes``, une fonction pure testable sans serveur ; et
le module importe ``kubernetes`` au chargement, bibliothèque fournie par
la dépendance ``odoo_herd``. Le menu est réservé au groupe
``proxmox_tenant.group_proxmox_manager``, et le rafraîchissement de 60
secondes ne tourne que tant que la page est ouverte.

Installation
============

Aucune dépendance déclarée dans le manifeste, mais le module importe
``kubernetes`` au chargement (``from kubernetes import client``). Cette
bibliothèque est déclarée par ``odoo_herd``
(``external_dependencies.python``), dont le module dépend : elle est
donc installée avec lui. L'environnement Odoo doit fournir
``kubernetes``, sinon le chargement du module échoue.

Dépend de ``proxmox_tenant``, ``odoo_herd`` et ``web``, installés
automatiquement ; aucun ordre manuel. Sans serveur Proxmox synchronisé
ni cluster déclaré, le tableau s'ouvre mais n'a rien à montrer.

Configuration
=============

Aucun réglage propre, vérifié dans le module : il n'expose ni
``res.config.settings``, ni paramètre système, ni groupe, et son
manifeste ne charge que ``views/menus.xml``.

Le menu *Salle de contrôle* est réservé au groupe
``proxmox_tenant.group_proxmox_manager`` (groupe du module voisin, pas
du module). La configuration réelle se fait dans les modules qui portent
la donnée : URL et jeton des serveurs dans ``proxmox_tenant``, clusters
et kubeconfigs dans ``odoo_herd``. Sans au moins un serveur synchronisé
ou un cluster déclaré, le tableau n'a rien à montrer.

Usage
=====

Pour utiliser ce module, il faut :

1. Disposer d'au moins un serveur Proxmox synchronisé par
   ``proxmox_tenant`` (*Proxmox* > *Serveurs*) : sans miroir local, le
   tableau n'a rien à montrer.
2. Pour la partie Kubernetes, avoir déclaré au moins un cluster dans
   Odoo Herd : les clusters et leurs kubeconfigs sont lus dans
   ``k8s.cluster``.
3. Attribuer à l'usager le groupe **Proxmox — Gestionnaire** (ou un
   groupe qui l'implique) : le menu est réservé à ce groupe.
4. Ouvrir *Salle de contrôle* > *Proxmox*.

Le tableau se rafraîchit toutes les 60 secondes ; le bouton *Rafraîchir*
force la relecture. Le bandeau indique la date de la dernière
synchronisation Proxmox, ou « Aucune synchronisation enregistrée ».

Les cartes résument le nombre de serveurs, de nœuds et de machines, les
machines en fonction et arrêtées, et la mémoire utilisée sur la mémoire
totale. La table des nœuds donne l'état, le CPU et la mémoire de chacun
; la table Kubernetes donne, par cluster, la joignabilité, les nœuds
prêts et les déploiements indisponibles, avec le détail de l'erreur si
le cluster ne répond pas.

Known issues / Roadmap
======================

Les chiffres Proxmox viennent des miroirs de ``proxmox_tenant`` : entre
deux synchronisations, ils peuvent être périmés. Le bandeau affiche la
date de la dernière synchronisation, ou « Aucune synchronisation
enregistrée », mais rien ne force une relecture avant l'affichage.

Les clusters sont lus séquentiellement dans ``kubernetes_snapshot``,
sans délai d'attente paramétré par cluster : un cluster lent allonge
l'appel pour tous les autres. Une erreur est bien capturée par cluster
(elle n'est pas levée), mais elle n'empêche pas cet allongement.

Les seuils d'alerte mémoire (90 % avertissement, 97 % critique) sont des
constantes du module, non réglables. Les alertes sont recalculées à
chaque lecture : elles ne sont ni stockées, ni notifiées, ni
historisées.
