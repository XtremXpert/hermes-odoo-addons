Administrer un serveur **Mailcow** depuis Odoo, par son API REST v1
(``X-API-Key``).

- gestion des domaines, boîtes mail et alias du serveur Mailcow ;
- création, mise à jour et suppression sur le serveur par des boutons ;
- synchronisation (import) depuis le serveur Mailcow ;
- mots de passe initiaux et de réinitialisation générés par Odoo,
  affichés une seule fois et jamais stockés, ni dans une fiche ni dans
  un assistant ;
- droits vérifiés dans chaque méthode, pas seulement sur les boutons :
  le groupe Lecture et synchronisation (pour les agents) lit et aligne
  Odoo sur le serveur, sans jamais écrire sur Mailcow ni voir de mot de
  passe ; le groupe Utilisateur crée et met à jour ; le groupe
  Gestionnaire supprime, synchronise et change les mots de passe ;
- une écriture n'est jamais rejouée : après une erreur passagère ou un
  délai dépassé (30 s), le résultat est annoncé incertain, à relire par
  une synchronisation ;
- configuration de la connexion (URL et clé API) dans les réglages ;
- tableau de bord : occupation des domaines, plafonds atteints, pression
  des quotas.

Use Cases / Context
===================

Administrer Mailcow depuis Odoo est une chose — les fiches, les
écritures, les réglages de connexion : c'est ``mailcow_tenant`` — en
donner une vue d'ensemble lisible en est une autre. Ce module porte
seulement la couche de présentation : deux tableaux de bord OWL,
l'ensemble du serveur et un par domaine, et les alertes qui en
découlent. Le séparer évite de mêler une interface à un modèle de
données réutilisable par les agents.

Les chiffres viennent des objets de ``mailcow_tenant``, donc de la copie
locale. Le rafraîchissement automatique (30 secondes) ne relit que
l'état d'Odoo et n'interroge jamais Mailcow ; tirer du serveur reste un
geste explicite, par « Synchroniser depuis Mailcow » ou « Synchroniser
ce domaine ». Ce choix évite de mettre la charge d'un tableau de bord
ouvert sur le serveur de messagerie. Les alertes viennent des données du
module voisin et sont triées à l'affichage par gravité ; un clic ouvre
la liste filtrée correspondante.

Deux contraintes d'installation sont assumées dans le manifeste : les
assets doivent être chargés après ``web/static/src/module_loader.js`` —
sinon le client web meurt au chargement, sans erreur côté serveur — et
un ``pre_init_hook`` adopte les xmlids du tableau de bord renommés
``mailcow_admin`` → ``mailcow``. La clé API reste celle de
``mailcow_tenant`` ; elle peut venir de l'environnement, et elle est
ignorée sur une base neutralisée.

Installation
============

Aucune dépendance externe : le module ne déclare ni dépendance Python ni
binaire (``external_dependencies`` absent) et s'installe comme un module
Odoo standard. Il dépend de ``mailcow_tenant``, installé automatiquement
; installer ``mailcow_tenant`` d'abord, ``mailcow`` ensuite, comme la
dépendance l'impose.

``pre_init_hook`` (``adopt_dashboard_xmlids``) renomme les xmlids de
tableau de bord de ``mailcow_admin`` vers ``mailcow`` : sur une
installation neuve, il ne trouve rien et ne fait rien. Les assets sont
déclarés après ``web/static/src/module_loader.js`` dans le manifeste ;
aucun réglage manuel.

Configuration
=============

Dans Réglages → **Mailcow**, renseigner l'URL du serveur, puis tester la
connexion.

Clé API, de préférence hors de la base : la variable d'environnement
``MAILCOW_API_KEY`` du conteneur Odoo, alimentée par un Secret
Kubernetes copié depuis Vaultwarden. Elle l'emporte sur le réglage, qui
est alors masqué. Elle est ignorée sur une base neutralisée
(``database.is_neutralized``) : un staging cloné n'agit jamais sur le
vrai serveur.

À défaut, la clé saisie dans les réglages est stockée dans
``ir.config_parameter`` (``mailcow.api_key``), donc dans les sauvegardes
et les clones de la base.

Usage
=====

Pour utiliser ce module, il faut :

1. Avoir installé et configuré ``mailcow_tenant`` (URL et clé API du
   serveur) : ce module s'appuie sur ses objets et ses réglages.
2. Attribuer un groupe Mailcow à l'usager — *Utilisateur* ou
   *Gestionnaire* — pour qu'il ouvre le menu *Mailcow*.
3. Ouvrir *Mailcow* > *Vue d'ensemble* : les alertes à traiter
   (plafonds, comptes dormants, alias cassés) s'affichent en cartes ; un
   clic ouvre la liste filtrée correspondante.
4. Choisir l'onglet *Domaines*, *Boîtes* ou *Alias* pour le détail,
   chercher et trier les colonnes ; un clic sur un domaine ouvre son
   tableau de bord, un clic sur une boîte ou un alias ouvre sa fiche.
5. Cliquer **Synchroniser depuis Mailcow** pour relire le serveur, ou
   **Rafraîchir maintenant** pour ne relire que l'état local ; la
   bascule *Rafraîchir tout seul, toutes les 30 secondes* entretient
   l'affichage sans interroger Mailcow.

Sur le tableau d'un domaine, **Nouvelle boîte** et **Nouvel alias**
créent les fiches correspondantes ; **Synchroniser ce domaine** n'aligne
que ce domaine ; **Tous les domaines** revient à la vue d'ensemble. Les
créations, mises à jour et suppressions sur le serveur restent celles de
``mailcow_tenant``.

Known issues / Roadmap
======================

Ce module ne fait que présenter : les créations, mises à jour et
suppressions sur le serveur restent celles de ``mailcow_tenant``, dont
il dépend. Il ne peut donc pas être installé seul.

Le rafraîchissement automatique de 30 secondes relit l'état local d'Odoo
et n'interroge pas Mailcow ; les chiffres peuvent donc être périmés
entre deux synchronisations explicites. L'écriture incertaine (délai de
30 secondes) documentée dans la DESCRIPTION concerne les écritures de
``mailcow_tenant``, pas ce tableau de bord.

La clé API vient de la variable d'environnement ``MAILCOW_API_KEY`` ou,
à défaut, de ``ir.config_parameter`` (``mailcow.api_key``) — donc des
sauvegardes et des clones de la base. Elle est ignorée sur une base
neutralisée, mais le module lui-même n'a pas de réglage propre.

Deux contraintes de maintenance sont inscrites au manifeste : les assets
doivent être chargés après ``web/static/src/module_loader.js``, sinon le
client web meurt au chargement sans erreur serveur ; et
``pre_init_hook`` n'adopte que les xmlids dont le nom contient
``tableau`` — les autres sont adoptés par ``mailcow_tenant``.
