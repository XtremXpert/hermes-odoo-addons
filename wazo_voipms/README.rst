Pont entre **Wazo** (PBX, module ``wazo_phone``) et **VoIP.ms** (trunk
RTC, module ``voipms_sms``).

Deux directions :

- **Sortant** — ``wazo.voipms.trunk`` provisionne un sous-compte SIP
  chez VoIP.ms, un endpoint+trunk+outcall côté Wazo. Les usagers
  composent ``<préfixe><numéro>`` pour sortir par ce trunk.
- **Entrant** — un DID VoIP.ms (``voipms.did``) peut être routé vers une
  destination Wazo (utilisateur ou groupe d'appel) : le module crée
  l'``incall`` dans ``from-extern`` puis bascule le routage VoIP.ms en
  ``sip:<DID>@<hôte Wazo>``.

Use Cases / Context
===================

Un tenant Wazo doit joindre le RTC et recevoir ses numéros.
``wazo_voipms`` fait le pont avec VoIP.ms dans les deux sens : un
sous-compte SIP (ou IAX2) VoIP.ms, un endpoint, un trunk et un outcall
côté Wazo pour sortir par ``<préfixe><numéro>`` ; et, pour l'entrant, un
incall dans ``from-extern`` puis un routage ``sip:<DID>@<hôte Wazo>``
posé chez VoIP.ms.

Le provisionnement est idempotent par identifiants distants : chaque
étape (VoIP.ms puis Wazo) note ce qu'elle a créé, et *Réessayer* reprend
un provisionnement en erreur sans recréer l'existant. Un sous-compte
VoIP.ms est mono-protocole (SIP ou IAX2) : le choix décide de la jambe
Wazo ↔ VoIP.ms, les usagers restant en WebRTC/SIP vers Wazo. IAX2
traverse le NAT sans port ouvert et l'entrant arrive par
l'enregistrement ; SIP exige que Wazo soit joignable publiquement. Un
trunk porte un ``tenant_slug`` : chaque Odoo de tenant ne route que ses
propres DIDs, quand l'instance de la plateforme les voit tous.

La destination d'un entrant est unique — utilisateur, groupe, file, IVR,
conférence ou messagerie —, validée par contrainte : Wazo n'accepte
qu'une destination par incall. L'assistant de première configuration
enchaîne trunk, usager et groupe d'appel en réutilisant les actions
existantes. Le module dépend de ``wazo_tenant`` et de ``voipms_sms``,
dont il réutilise les clients ; il s'installe sur l'Odoo du tenant, et
sur celui de la plateforme qui doit voir tous les DIDs.

Installation
============

Aucune dépendance externe : le module réutilise le client Wazo de
``wazo_tenant`` et le client VoIP.ms de ``voipms_sms``, tous deux en
``urllib``, et son manifeste ne déclare ni ``external_dependencies``
Python ni binaire. Il dépend de ``wazo_tenant`` et ``voipms_sms`` et
s'installe comme un module Odoo standard.

Les deux modules dépendants doivent être configurés (URL et jeton Wazo,
utilisateur et jeton VoIP.ms) et le serveur Wazo joignable en SIP par
VoIP.ms pour le routage entrant ; ce sont des prérequis d'usage, pas
d'installation.

Configuration
=============

Prérequis :

- ``wazo.url`` + ``wazo.api_key`` configurés (module ``wazo_phone``) ;
- ``voipms.api_username`` + ``voipms.api_token`` configurés (module
  ``voipms_sms``) ;
- le serveur Wazo joignable en SIP par VoIP.ms (port 5060/5061 public)
  pour le routage entrant.

Menu **Téléphonie Wazo → Trunks VoIP.ms** pour le trunk sortant ;
l'onglet **Pont Wazo** apparaît sur les fiches DID.

Usage
=====

Pour utiliser ce module, il faut :

1. Avoir configuré ``wazo_phone`` et ``voipms_sms`` (URL et jeton Wazo,
   utilisateur et jeton VoIP.ms), et rendu le serveur Wazo joignable en
   SIP par VoIP.ms.
2. Ouvrir *Téléphonie Wazo* > *Trunks VoIP.ms* et créer un trunk : nom,
   protocole (*SIP* ou *IAX2*), serveur (*POP*) VoIP.ms, identifiant et
   mot de passe du sous-compte (laisser vide pour les faire créer au
   provisionnement), indicatif d'appelant sortant et préfixe de sortie
   (par défaut ``9``).
3. Cliquer **Provisionner** : le module crée le sous-compte SIP chez
   VoIP.ms, puis l'endpoint, le trunk et l'outcall côté Wazo. **Vérifier
   la connexion** contrôle l'enregistrement ; **Réessayer** reprend un
   provisionnement en erreur ; **Retirer** supprime le trunk du serveur
   (les numéros qui en dépendent cessent de sonner).
4. Pour les appels sortants, composer ``<préfixe><numéro>`` depuis un
   poste Wazo.
5. Pour router un DID entrant, ouvrir sa fiche dans *SMS VoIP.ms* >
   *DIDs* : le groupe *Pont Wazo (appels)* apparaît sur la fiche,
   choisir le type de destination (utilisateur, groupe d'appel, file,
   menu vocal, conférence ou messagerie vocale) puis cliquer **Router
   vers Wazo**. Le module crée l'incall ``from-extern`` puis bascule le
   routage VoIP.ms. **Retirer le routage** remet le DID en
   ``sys:hangup``.

Known issues / Roadmap
======================

Limites connues
---------------

- **Un protocole par trunk** : un sous-compte VoIP.ms est mono-protocole
  (``protocol`` : SIP ou IAX2, mesuré) ; faire cohabiter SIP et IAX2
  demande deux trunks.
- **Routage entrant en deux moitiés** : l'incall est créé côté Wazo,
  puis le routage est basculé chez VoIP.ms (``setDIDRouting``). Les deux
  appels ne sont pas transactionnels : un échec partiel peut laisser un
  incall sans routage, que la reprise idempotente rattrape.
- **SIP entrant exposé** : le routage en ``sip:`` exige que Wazo soit
  joignable publiquement (port 5060/5061) ; IAX2 évite le port ouvert en
  passant par l'enregistrement.
- **Une destination par DID** : la contrainte n'accepte qu'un seul des
  champs de destination (utilisateur, groupe, file, IVR, conférence,
  messagerie).
- **Retrait destructeur pour les numéros** : *Retirer* supprime le trunk
  du serveur ; les numéros qui en dépendent cessent de sonner
  (``readme/USAGE.md``).
- **Secrets SIP en clair** : ``voipms_password`` est un ``Char`` réservé
  au groupe gestionnaire, stocké sans chiffrement dans la base.
- **Aucune tâche de fond** : provisionnement, vérification et routage
  sont des gestes manuels ; pas de cron.
