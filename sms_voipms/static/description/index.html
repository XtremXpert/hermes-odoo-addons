SMS via VoIP.ms

Envoie les SMS d’Odoo par l’API REST de VoIP.ms au lieu du service payant IAP d’Odoo.

Le réglage se fait par société : « Envoyer via Odoo (IAP) » (défaut) ou « Envoyer via VoIP.ms ». Dans le second cas, le composeur SMS, le CRM, les modèles de SMS, l’automatisation et le marketing de masse passent tous par VoIP.ms, et le DID expéditeur est choisi dans les réglages de la société.

Le module s’appuie sur voipms_sms (client REST, segmentation à 150 caractères, gestion des DID, identifiants API) et sur l’abstraction fournisseur d’Odoo 20 — la même que celle utilisée par sms_twilio.

Limites connues :

  • envoi seulement : les réponses des destinataires ne remontent pas dans Odoo (une spec ultérieure pourra les rattacher au chatter à partir du suivi conservé à l’envoi) ;
  • NANP seulement (Canada / États-Unis) ;
  • sms_twilio et sms_voipms déclarent tous deux le champ sms_provider : les installer ensemble fait perdre une option de la sélection (limite d’Odoo 20 pour les modules fournisseurs), donc ne pas installer les deux.

Use Cases / Context

Odoo 20 envoie les SMS par le service IAP d’Odoo : chaque message consomme un crédit acheté, et le compte est lié à Odoo, pas au fournisseur téléphonique de l’organisme. Diverse-Cité possède déjà un compte VoIP.ms dont des DID ont le SMS activé, et le module voipms_sms y envoie des SMS depuis une boîte d’envoi autonome.

Le besoin métier est de faire passer les SMS d’Odoo — ceux que les utilisateurs envoient depuis le chatter, le CRM, les modèles de SMS et les campagnes — par ce compte VoIP.ms, sans changer d’outil, sans toucher au cœur d’Odoo et sans acheter de crédits IAP.

Le module est donc un pont : il ne réimplémente ni le composeur, ni les modèles, ni le suivi d’Odoo ; il remplace seulement le transport (le fournisseur), par société, en s’appuyant sur les mêmes points d’extension que sms_twilio.

Installation

Dépendances

  • Odoo 20.0 Community.
  • Module voipms_sms (client REST, segmentation, DID) — installé automatiquement comme dépendance.
  • Module sms (framework SMS d’Odoo).
  • Un compte VoIP.ms avec l’API activée, un jeton, et un DID dont le SMS est activé.

Aucune bibliothèque Python supplémentaire : le client existant utilise urllib de la bibliothèque standard.

Configuration

Prérequis VoIP.ms

  1. Activer l’API dans le portail VoIP.ms (menu SOAP and REST/JSON API) et créer un jeton.
  2. Autoriser l’adresse IP publique du serveur Odoo dans la liste blanche de l’API.
  3. Activer le SMS sur le DID expéditeur (DID Numbers → SMS).

Réglages Odoo

  1. Réglages → section SMS VoIP.ms : renseigner l’utilisateur API et le jeton, puis Tester la connexion.
  2. Réglages → SMS : choisir « Envoyer via VoIP.ms » et le DID expéditeur.
  3. Enregistrer.

Pour revenir au service Odoo, choisir « Envoyer via Odoo (IAP) » : les crédits IAP redeviennent la voie d’envoi, sans réinstallation.

Le DID proposé est limité aux numéros dont le SMS est activé chez VoIP.ms (champ sms_enabled synchronisé par voipms_sms).

Usage

Envoyer un SMS comme d’habitude : composeur du chatter, action « Envoyer un SMS », modèle de SMS, automatisation ou marketing de masse. Le message part par VoIP.ms et le SMS passe à l’état Envoyé (en attente de livraison chez VoIP.ms), puis à Livré lorsque le fournisseur le confirme.

Les identifiants renvoyés par VoIP.ms sont conservés sur le suivi (sms.tracker) et restent visibles sur la fiche du SMS, même après le nettoyage des SMS envoyés.

Si VoIP.ms refuse l’envoi (numéro invalide, hors NANP, crédit épuisé, panne), le SMS passe à l’état Erreur avec le motif du fournisseur ; il est possible de le renvoyer depuis la liste des SMS.

Known issues / Roadmap

Limites connues

  • Envoi seulement : les réponses des destinataires ne remontent pas dans Odoo.
  • NANP (Canada / États-Unis) seulement.
  • Pas d’accusé de livraison poussé par VoIP.ms : le SMS reste Envoyé jusqu’au nettoyage, sauf si le fournisseur confirme la livraison.
  • sms_twilio et sms_voipms sont mutuellement exclusifs (même champ sms_provider).

Évolutions envisagées

  • Réponses entrantes : contrôleur HTTP, URL SMS du DID, rattachement au chatter à partir du suivi conservé à l’envoi.
  • Accusés de livraison par interrogation périodique (getSMS).
